## 1. 定稿设计(决策点 A–L)

### 0. 总纲(v1 继承，一条修订)

reaper 是 **MySQL 真相源上的纯周期对账器**：候选扫描全部为无锁普通 SELECT;每一项处置在短事务内「锁后复核 + CAS 收置」完成。Redis 锁仅做 leader 去重(fail-open 效率件)，**正确性结构性不依赖任何锁、时钟或 Redis**——ARCHITECTURE.md:53「Redis 锁仅留给 reconciler 选主」的字面落地，也是「断 Redis 30s 仍收敛」验收成立的结构前提。

处置语义全景(与 DDL 状态枚举逐字对齐，已对照 `internal/db/migrations/0001_init.up.sql` 实文):

| 遗留形态 | 扫描 | 收口 |
|---|---|---|
| attempt RUNNING 心跳陈旧(worker 死 / asynq MaxRetry=1 穷尽 archived) | ①attempt | DEAD(`heartbeat_lost`)→ 预算内 Redispatch / 耗尽标 FAILED(fail-fast 同事务镜像) |
| node EXECUTING 过 deadline(worker 活但挂死 / 派发事件丢失) | ②node | 谓词锁后复核 → DEAD(`deadline_exceeded`) 或 **ExtendNodeDeadline 重挂**(迟到启动，攻击 7)/ **无活 attempt 分支 B**(攻击 6/10) |
| wf 已终态、节点留 EXECUTING(fail-fast 遗留，扫描靶 a) | ③orphan | 节点 CANCELLED;陈旧 RUNNING attempt 附带 DEAD |
| wf PENDING 滞留(exec: 事件死/丢) | ④a | `FinishExecution(FAILED,'reconciler_timeout')`(wf 锁先行，与 Start 同例外) |
| wf RUNNING 全节点终态但终态判定未落(sched.go:521-525 预留兜底点) | ④b | 委托 `scheduler.FinishIfDone` |
| audit_log 分区水位 / outbox DISPATCHED 7 天 | janitor | ADD/DROP PARTITION(幂等+双守卫)/ 批量 DELETE |

**v1 修订一条总纲级结论**：扫描②不再只是「判死扫描」，它与扫描①共用同一处置事务 `reapAttempt`,其中显式定义「无 RUNNING attempt」分支(攻击 6/10 的 CRITICAL/HIGH 缺口)——v1 的「缺行→skip」会把「EXECUTING 节点 + 零 attempt 行 / attempt 已终态 + 派发事件死」的执行永久卡在 RUNNING,直接违背验收「无人工干预达终态」。

### A. 扫描 SQL

**四条候选扫描，每 tick 顺序执行、逐作业错误隔离(log+continue);全部普通 SELECT,无 FOR UPDATE / SKIP LOCKED**。理由(v1 论证成立，保留)：处置事务要按 node→attempt→wf 序锁多表，扫描语句若先锁 attempt 再锁 node 即自造 AB-BA(与 Complete 的全行集锁、与心跳的 attempt→wf 均成环)；安全性由处置事务内「FOR UPDATE 锁后复核 + CAS 谓词」结构性保证，选主失效双跑收敛为「先者胜、后者复核 0 行空提交跳过」。relay 可用 SKIP LOCKED 是因其扫描行即唯一锁目标(run.go:126-133 单表单事务原子标记)，形态本质不同，不迁移。批量 LIMIT 100,打满循环排空(单 tick 每扫描上限 1000 行)，批满记 backlog warn(接 T6.4)。

**攻击 14 吸收——扫描③驱动从 wf 侧改 node 侧**：v1 的「终态 wf JOIN」驱动集无界(终态行永不清，谓词只带上界，稳态每 tick 全量走历史)。改为 **node 侧驱动**，成本上界 = EXECUTING 行数(活执行 ≤ worker 并发 + 孤儿少量)，且孤儿任意年龄都可检出、无需 24h 窗:

```sql
-- ① attempt 判死候选(idx_attempt_status_heartbeat(status,heartbeat_at) 纯索引区间)
SELECT id, node_execution_id, execution_id
  FROM node_attempt
 WHERE status='RUNNING' AND heartbeat_at < NOW(3) - INTERVAL ? MICROSECOND   -- ? = grace.Microseconds()
 LIMIT 100;

-- ② 节点 deadline 候选(idx_node_status_deadline;NULL deadline 谓词恒假天然排除 branch)
--    skew margin 兑现 nodecas.go:22-23 契约「deadline 是唯一应用侧时间,偏差由 reconciler 阈值×N 吸收」
--    margin = SCAN_INTERVAL(派生,不设独立 env);WAITING_APPROVAL 半边归 T4.3,刻意不扫
SELECT id, execution_id
  FROM node_execution
 WHERE status='EXECUTING' AND deadline_at < NOW(3) - INTERVAL ? MICROSECOND  -- ? = scanInterval.Microseconds()
 LIMIT 100;

-- ③ 孤儿候选(攻击 14 吸收:node 侧驱动,idx_node_status_deadline status='EXECUTING' 前缀
--    → wf 主键点查;2m 静默窗避开 Complete 提交/finishIfDone 的在飞窗口)
SELECT n.id, n.execution_id
  FROM node_execution n
  JOIN workflow_execution w ON w.id = n.execution_id
 WHERE n.status = 'EXECUTING'
   AND w.status IN ('SUCCEEDED','FAILED','CANCELLED')
   AND w.last_activity_at < NOW(3) - INTERVAL ? MICROSECOND                 -- ? = 2m(静默窗,常量)
 LIMIT 100;

-- ④a PENDING 执行候选 / ④b RUNNING 终态补判候选(同 idx_exec_status_activity;
--    status 等值前缀 ⇒ 驱动集 = 该 status 全部行 = 活跃集,天然有界;WAITING_APPROVAL 合法挂起刻意排除)
SELECT id FROM workflow_execution
 WHERE status='PENDING' AND last_activity_at < NOW(3) - INTERVAL ? MICROSECOND  -- PENDING_TTL
 LIMIT 100;
SELECT id FROM workflow_execution
 WHERE status='RUNNING' AND last_activity_at < NOW(3) - INTERVAL ? MICROSECOND  -- EXEC_STALE
 LIMIT 100;
```

索引全部为 0001 既建(idx_attempt_status_heartbeat:174、idx_node_status_deadline:130、idx_exec_status_activity:89、idx_outbox_poll:208),**零新迁移**。RR 快照略旧无害：处置事务内锁后复核(当前读 + NOW(3) 谓词)是唯一裁决点。扫描靶 b(asynq 穷尽 archived 后 attempt 留 RUNNING)= 扫描①(心跳停更→陈旧)，不设专用扫描。

### B. 判死 grace 公式与配置

`DEAD_GRACE` 默认 **45s = 3×(RetryDelay 5s + HeartbeatInterval 10s)**,公式兑现 T2.3 移交硬约束①(worker.go:235-243:接管重置是尽力语义，失败仅 warn;最坏陈旧 = RetryDelay+HeartbeatInterval=15s,余量 3×)。判死谓词全部 DB 端 `NOW(3)`(连接契约 SET time_zone='+00:00',DDL 头注)，应用时钟漂移不入判定。

**攻击 3 吸收——公式必须有执行点强制，v1 的 warn 漏了 RetryDelay 一半**:ConfigFromEnv/Validate 增加跨进程硬校验:

```
读 BRAID_WORKER_RETRY_DELAY、BRAID_WORKER_HEARTBEAT_INTERVAL(worker/config.go:93-96 同名键):
  两者均可读且 grace ≤ retry+hb            → 启动即败(同机同 env 是共享真源)
  两者均可读且 grace < 3×(retry+hb)        → warn(留观察)
  不可读                                    → 保持 v1 行为:仅当 grace < 3×HeartbeatInterval 可读时 warn
```

Validate 硬下限 20s(env 路径;>15s 陈旧上界 + 余量)；测试经 Config 字面量注入毫秒级值，`RunOnce` 不做 Validate(校验属启动路径)。

**验收时序恒等式(攻击 5/11 吸收后重推，写入 config 注释与测试注释)**:
- **相位钉死(issue 验收的可测化口径)**：「断 Redis 30s」的停机窗 = **[t0, t0+30],t0 = kill 时刻**。检出时刻 T_d ≥ 末次心跳 + grace ≥ t0 + 45 − 10 + 5 = t0+35(末次心跳最坏提前一个心跳间隔)> t0+30 ⇒ **重派事务的 outbox 写入结构性落在停机窗之外**，relay 退避链(5s→20s→80s,relay/config.go:20-22)不被触发，恢复后 ~1s 投递。
- 检出 T_d ≤ grace+scan = 75s;投递+claim+重执行+Complete+finishIfDone ≈ 数秒(桩 executor 毫秒级)⇒ 终态 ≤ ~80s < 90s = 3×scan,**余量 ~10s 成立**。v1 的「余量吸收 relay 投递」论证仅在钉死相位后成立，此为攻击 11 的吸收结论。

### C. DEAD 收口 + 重派的事务形状(reapAttempt,统一处置事务)

**新增引擎 helper 两个(全部新增 CAS 面；均落 engine 包，遵守 nodecas.go:15-17「version+1 ⇒ affected==matched」不变量)**:

```go
// attempt.go —— 兑现预留 DEAD 边(attempt.go:73、states.go:62)
// CloseAttemptDead:RUNNING→DEAD(reaper 判持有者已死)。不写 finished_at(DDL:169 DEAD 恒 NULL)。
// 谓词仅 status='RUNNING':新鲜度由调用方事务内 FOR UPDATE 复核承载(行锁下心跳/收口不可并发改行,
// 谓词再含新鲜度只会把 0 行语义二元膨胀为三元,零安全性增益——维持 v1 否决结论)。
// 0 行 → FOR UPDATE 复查 → ErrNotFound / *ConflictError{Observed}(与 CloseAttempt 同形)。
func CloseAttemptDead(ctx context.Context, q DBTX, attemptID uint64, code, msg string) error

// nodecas.go —— 攻击 7 吸收:迟到启动 attempt 的一次性重挂(status-preserving,attempts 不变)
// ExtendNodeDeadline:仅刷 EXECUTING 节点 deadline。不触 status_changed_at(非状态迁移);
// deadline_at 必变值 ⇒ version+1 不变量保持。用途与 RedispatchNode 互补:不烧 attempt 预算。
func ExtendNodeDeadline(ctx context.Context, q DBTX, id uint64, expectVer uint32, deadline time.Time) (uint32, error)
```

**处置事务 `reapAttempt`(四类节点级候选共用；外层 engine.Transient(1213/1205) 抖动重试 ≤3,照抄 sched.go:397-414 循环；每候选一事务)**。三个扫描入口在事务内**统一走同一分派树**——v1 的「锁后复核清单」补全为五项：attempt 收口态、**心跳新鲜(无条件、与入口无关，攻击 17)**、**deadline 复活(攻击 9)**、wf 当前读、**attempt 存在性三分(攻击 6/10)**:

```
reapAttempt(candidate):
  engine.WithTx:
    -- [1] 锁 node 行(node→attempt→wf 序第一锁)
    SELECT id,node_id,type,status,version,attempts,max_attempts,worker_id,deadline_at
      FROM node_execution WHERE id=? FOR UPDATE
    -- [2] 入口谓词锁后复核(攻击 9:扫描②候选在 Complete 并发 Redispatch 刷新 deadline 后
    --     不再判死;扫描①候选在心跳复活后不再判死)
    若 entry==deadline 且 deadline_at >= NOW(3)-skew 且 [3] 无陈旧证据 → skip
    -- [3] 锁当前 attempt 行(uk_attempt 前缀定位,攻击 6 吸收:钉死
    --     WHERE node_execution_id=? AND attempt_no=<node.attempts>,禁 status 打头的无索引过滤;
    --     不变量:attempt_no RUNNING ⇒ attempt_no==node.attempts,因 Redispatch/Complete 均先收口旧行)
    SELECT id,status,heartbeat_at,started_at,worker_id
      FROM node_attempt WHERE node_execution_id=? AND attempt_no=? FOR UPDATE
    分派:
    ├─ node.status ≠ EXECUTING(人工 Cancel 等残留的陈旧 RUNNING attempt,v1 补分支保留)
    │     行存在且 RUNNING → CloseAttemptDead('stale_attempt')+TouchExecution+warn;否则 skip
    ├─ 行 = RUNNING 且 heartbeat_at ≥ NOW(3)-grace(活性保护,无条件前置——攻击 17)
    │     entry==deadline 且 deadline 过期 且 started_at ≥ deadline_at(迟到启动,攻击 7)
    │        → engine.ExtendNodeDeadline(now+NodeTimeout(type))+TouchExecution+info;return
    │     否则 skip(活 worker 绝不被抢写)
    ├─ 行 = RUNNING 且心跳陈旧
    │     code = (deadline_at < NOW(3)-skew) ? 'deadline_exceeded' : 'heartbeat_lost'   -- 攻击 9:收口码由锁内实测谓词决定
    │     CloseAttemptDead(code, msg=陈旧时长+行内 worker_id(注明首任))
    │     → [4] 收口分派
    └─ 行 = 无行 / 非 RUNNING(攻击 6/10 吸收:分支 B)
          -- 活派发事件闸(防双派发;LIKE 前缀含 ':' 定界符,'att:12:%' 不匹配 'att:123:x')
          SELECT COUNT(*) FROM outbox
           WHERE task_id LIKE CONCAT('att:', ?, ':%')
             AND (status='PENDING'
                  OR (status='DISPATCHED' AND dispatched_at >= NOW(3) - INTERVAL ? MICROSECOND))  -- DISPATCH_STALE
          count>0 → skip(warn+计数,可观测非静默;PENDING 经 relay 退避 ~11.8min 自灭为 DEAD,
                       DISPATCHED 活窗界于 DISPATCH_STALE,之后下轮收敛)
          → [4] 收口分派(无 attempt 可收)

    -- [4] 锁 wf 行(最后,当前读)
    SELECT status FROM workflow_execution WHERE id=? FOR UPDATE
    switch wf.status:
      终态              → engine.CancelNode(node, ver)          -- 靶 a:收口目标态 CANCELLED(E 节)
      WAITING_APPROVAL  → warn 数据缺陷(T4.1 契约:挂起须 attempt 已收口,DDL:104-105);return
      RUNNING 且 attempts < max_attempts
                        → engine.RedispatchNode(ver, {WorkerID:"reaper:<id>",
                            DeadlineAt: now+scheduler.NodeTimeout(type)})
                        + outbox.Append(att:<nodeExecID>:<attempts+1>, node.task_enqueue,
                            scheduler.NodeTaskPayload{...}, Queue)   -- 同事务,新 TaskID 零冲突
                        + engine.TouchExecution
      RUNNING 且耗尽    → engine.FailNode(ver, 行内 worker_id, 'attempts_exhausted', msg)
                        + engine.FinishExecution(FAILED, nil, 'node_failed', msg)  -- fail-fast 同事务镜像
                                                                           -- FinishExecution 自刷 last_activity_at
```

要点：
- **分支 B 双收敛(攻击 2/6/10)**:kill 在 claimAttempt 的 InsertAttempt 提交前 / handler 连续两次 infra 失败 archived / reaper 自己重派事件的 outbox 行经 relay 退避转 DEAD——三种「EXECUTING + 无活 attempt」形态都由扫描②在 deadline 到期后进入分支 B:预算内重派(新 attempt_no ⇒ 新 TaskID ⇒ uk_attempt 无行、与 archived 旧副本零冲突)或耗尽标 FAILED。最坏收敛时长 = deadline(10–30min)+ DISPATCH_STALE 窗，有界。
- **RedispatchNode 原样复用**(nodecas.go:137-158,D-t24 #5「平台重试的 claim 即本语句」，reaper 是第二触发源，注释「调度器(T2.4)」改「调度器/reaper」);`RequeueNode` 本任务不启用(EXECUTING→PENDING 后 advance 只挂 Start/Complete,PENDING 节点无扫描者会成永久孤儿)。
- 迟到 Complete 撞新链路：旧 asynq 副本重投 → claimAttempt 读 attempt DEAD → `already_final` 幂等返回(worker.go:229-232 实文)；新 attempt_no=新 TaskID。
- 双跑安全：后到实例在步骤 [3] 复核或 [4] CAS 必 0 行跳过。

### D. 重派 vs 标 FAILED 判定

(v1 全票结论，不变)预算源 = `node_execution.max_attempts`(Instantiate 时 DSL `retry.max_attempts` 快照，sched.go:288-293,CHECK [1,10]);判式与 completeOnce 逐字同式 `int(attempts) < int(maxAttempts)`(sched.go:478)。重派复用 RedispatchNode;耗尽路径照抄 Complete default 分支(sched.go:496-509),reaper 判死终局与 worker 业务终败终局在状态面零新形状。业务失败与 infra 判死**同池消耗预算**(「attempts ≤ 用户声明预算」不变量，重试权威单一)；max_attempts=1 时 kill -9 产物是 FAILED(验收允许终态二选一)，区分证据在 attempt 行(DEAD vs FAILED)+ error_code。`deadline_exceeded` 与 `heartbeat_lost` 分码，T6.4 聚合可辨。

### E. 扫描靶 a(fail-fast 遗留 EXECUTING 兄弟)

(v1 结论，一处钉死强化)目标态 = **CANCELLED**(经 `engine.CancelNode`,不写 error_code——「取消=平台裁决，失败=业务终局」是 DDL 词表既有语义)。按 attempt 行状态三分：形状1(RUNNING 且心跳新鲜)→ **跳过**(活 worker Complete 自愈：SUCCEEDED 路径 SucceedNode 在 termGuard 下仍执行，sched.go:457-466;FAILED 路径 termGuard 留 EXECUTING → 落形状3);形状2(RUNNING 且陈旧)→ 扫描①命中，处置事务 wf 终态分支 → DEAD+Cancel;形状3(attempt 已终态，termGuard 下迟到 FAILED 已被 CloseAttempt 收口，sched.go:476-477)→ 扫描③命中 → 仅 CancelNode。守卫 = 处置事务内 node FOR UPDATE 复核 + wf 当前读 + **形状1 跳过钉死为 W1 步骤 [3] 的无条件前置，与入口扫描无关(攻击 17 吸收，防实现按「心跳路径」字面只在扫描①启用)**。PENDING 后继不扫(「未到达」语义合法，进未决问题)；挂死 worker 下形状1 的滞留由 deadline 到期后扫描②强制收敛，互锁无洞。

## 2. 事务与锁序表(每条 reaper 写路径的语句序列)

全局锁序不变量(issue #4 回帖、wfcas.go:16-21 实文)：node 行(node_id 升序)→ node_attempt → workflow_execution(最后)；唯一例外 = Start 先拿 wf(前提:PENDING 执行无 claim/attempt、无并发 Complete)。

| 路径 | 语句序列(锁获取序) | 并发对方 | 无环论证 |
|---|---|---|---|
| W1 reapAttempt(①②③扫描共用，含分支 B) | ①`SELECT node FOR UPDATE` → ②outbox 活事件闸(普通 SELECT,**零锁**，仅分支 B)→ ③`SELECT attempt FOR UPDATE` → ④`CloseAttemptDead`/`ExtendNodeDeadline`(二选一)→ ⑤分支 CAS(node UPDATE:Redispatch/Extend/Fail/Cancel)→ ⑥`outbox.Append`(重派分支)→ ⑦`TouchExecution`(wf UPDATE;耗尽分支由 FinishExecution 自刷，终态分支省略) | Complete / 心跳 / 他 reaper | 全局偏序子集:Complete 持全行集时 reaper 阻塞在①(未持任何锁)；reaper 持 node 后 Complete 阻塞在 lockAllRows(sched.go:421-422,其 attempt/wf 步骤在后)；心跳只走 attempt→wf(worker.go:319-320),从不取 node 锁 ⇒ 无等待环。残余交错由 Transient(1213/1205)≤3 收敛 |
| W2 PENDING 执行判死(④a) | ①`SELECT wf FOR UPDATE`(**先 wf**,Start 同例外)→ ②复核仍 PENDING → ③exec: 活事件闸(普通 SELECT)→ ④`FinishExecution(FAILED,'reconciler_timeout')` | scheduler.Start | 例外前提保持:PENDING 执行 ⇒ 无 claim/attempt(wfcas.go:19-21;node EXECUTING 必然 wf 已 RUNNING——派发在 Start 事务内 StartExecution 之后，sched.go:341-352)⇒ 不存在 attempt→wf 在飞写者；与 Start 靠 wf 行锁互斥串行，败方复核后 skip |
| W3 RUNNING 终态补判(④b) | 委托 `scheduler.FinishIfDone`(新事务：读 node 集(无锁)→ outputs 物化 → `FinishExecution` status-only CAS) | Complete 提交后判定 | 与既有 finishIfDone 完全同路径(sched.go:534-588);双收口由 wf CAS 仲裁(Conflict 良性)；零 node/attempt 锁 |
| W4 audit 分区 ADD/DROP | janitor 专用 Conn、autocommit DDL、逐条执行；round 首条 `SET SESSION lock_wait_timeout=5` | 他 reaper 实例 / 长查询 | INFORMATION_SCHEMA 预检 + {1517,1493,1507} 容忍 + 复读确认 = 幂等；活执行守卫挡 1526;lock_wait_timeout=5 封顶 MDL 等待(攻击 8/12),等待超限仅弃本轮，扫描循环独立 goroutine 不受牵连 |
| W5 outbox 清理 | autocommit `DELETE … LIMIT 500` 批循环(无 ORDER BY) | relay 主循环 | 行集不相交(status 等值段)，锁窗不相交，唯一共享面 buffer pool |

**锁后复核裁决点(W1)**:候选 SELECT 与处置事务之间的 TOCTOU 全部在步骤①-④吸收——attempt 已收口→skip;心跳复活→skip(无条件);deadline 复活→skip 或按 started_at 分派 Extend;wf 状态以当前读为准。双 reaper/双 leader 下第二实例必在复核或 CAS 处 0 行空提交。

## 3. W1 哨兵拍板结论

**拍板：接受等价。** 语义升级为「attempt 已非 RUNNING ⇒ 收口权已旁落，终局已由收口方原子裁决」——reaper DEAD+重派后节点在 attempt N+1,放行迟到 attempt N 的 Complete 会与重派链路双推进；哨兵在 SucceedNode/FailNode 之前短路(sched.go:443-447 → 402-404)恰是裁决让位。区分成新错误类型零行为差(两分支都 return nil)且会烧 asynq MaxRetry 预算，纯税。

实现面(零行为变更):①`completeOnce` Conflict 分支用 CloseAttempt 复查免费带回的 `ConflictError.Observed`(errors.go:32-38)区分来源:`Observed==engine.AttemptDead`(states.go:69)→ `log.Warn("complete.discarded_by_reaper", attempt_id, node_execution_id, worker_outcome)`(成功结果被丢弃 = 发生过判死双执行的观测信号)；②`errAttemptAlreadyClosed` 注释补覆盖面与前提；③pin 测试:reaper 判 DEAD 后老 worker fake Complete 返回 nil 且 execution 状态不被二次改写。审计区分走数据层:reaper 收口 error_code='heartbeat_lost'/'deadline_exceeded',Complete 收口写业务码。

**攻击 1 带来的边界补强(不改变拍板，改变其前提的强度)**:F 原只覆盖「已在飞超 grace 的 worker 的迟到 Complete」;吸收攻击 1 后，「接管与判死同拍」的重叠执行由 worker 接管分支的锁内复核消灭(见 L.4)——迟到者要么在拿锁后确认行已 DEAD 而 ack 放弃，要么其心跳重置先落使 reaper 复核 skip。两向都在行锁上确定串行，无第三种交错。

## 4. worker_id 刷新拍板

**拍板：不刷新(首任归因)。** 理由：①DDL 列注释(0001:156)自证用途「T8.1 kill -9 场景的检测与归因」——检测走心跳陈旧度不读 worker_id,归因价值排序「首任(谁死的)」>「末任(谁重跑的)」，刷新会让 DEAD 行指向活实例，在最需要它的故障场景系统性失真；②attempt 表契约是「行创建 + 心跳单列刷新 + 收口一次终写」(0001:170),加非终态 worker_id UPDATE 打开第二条非终态写边；③接管链归因已有替代通道:`attempt.takeover` 结构化日志(worker.go:234)、RedispatchNode 把重派方写进 node_execution.worker_id、新 attempt 行(N+1)天然携带现任。偏差记录三落点：attempt.go 注释钉死「跨接管归因指首任」+ issue #4 回帖;`CloseAttemptDead` 的 error_message 携带行内 worker_id(注明首任);DEAD slog 同。T8.1 若实证需末任归因，增量方案 = 接管 CAS 单语句，接口已留好不返工。
