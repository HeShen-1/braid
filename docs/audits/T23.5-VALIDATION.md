发布协议或 T23.4 已交付的 `min_success` 规则。

## 机制与专项

- 发布按钮传入编辑器当前导出文档，Provider 先保存该快照再调用发布。
  保存失败保留编辑器、内容与未保存状态，零 publish 请求。
- 保存响应只更新对应工作区的保存基线，不覆盖请求之后的编辑；
  同一工作区在飞保存/发布不重复提交。首次建档期间名称暂时只读，
  Provider 另守名称时序，避免迟到 create 把改名后的本地文档锁到旧 id。
- 保存期间继续编辑会停止本次发布。publish 已经发出后若又有编辑，
  成功时将后续内容保留为本地未建档草稿，并说明先前版本已发布；
  失败时同样保留后续内容和未保存状态。
- 新建、换草稿、主导航、浏览器前进/后退及主动退出登录复用既有
  ConfirmLayer；取消后保留内容并归还入口焦点。刷新/关闭标签页使用
  浏览器原生 beforeunload。401 强制失效继续立即退出。
- URL 变化负责打开草稿；状态反向补 URL 只用于首次保存拿到 id。
  open 请求带序号与工作区快照，同 id 返回也先废弃旧请求，覆盖
  A→B 请求在飞→后退 A→B 迟到的交错，避免 URL 与画布不一致。
- 首次自动布局/补元数据与单纯选择节点不误报未保存；发布成功的
  列表态反馈及「查看已发布」出口保留。

先补最便宜的 Provider 反例，旧实现原生运行 `6 tests / 4 failed / 2 passed`:
直接发布未先保存、保存失败仍发布、在飞保存后继续编辑仍发布、旧保存
响应覆盖新建画布。修复后这些反例与新增导航/时序测试全部纳入全量门。
